# Decisions

## Owner-approved
- Browser app; React, TypeScript, Vite; Firebase Auth with Google Sign-In; Cloud Firestore; Firebase Hosting; Tiptap; CSS variables/plain CSS.
- Online-first; private per-user notes; automatic saving and cross-device sync.
- MVP formatting: bold, italics, headings, bullet lists, checklists.
- Unsaved edits must never be silently overwritten; conflicts need a visible, non-destructive recovery path.
- **Revision-aware deletion** (owner-approved, Option B). A delete carries the revision of the note the user intended to delete and is checked against the stored revision atomically (Firestore transaction). A matching revision permits the delete; a mismatch deletes nothing (the newer content survives) and tells the user the note changed. The user must then review the updated note and explicitly confirm deletion again; the app never retries a refused delete on its own, and merely receiving a newer revision does not authorize deleting it. Revision adoption and deletion authorization are separate things: a clean editor adopts and displays incoming revisions automatically, without any confirmation (as it does for any remote update), and loads the newer revision of a refused delete the same way; an editor holding unsaved edits shows its usual conflict choices instead. A delete expects the revision that is on screen at the moment the user confirms it, so a newer revision the editor has adopted and shown can be deleted by a new, explicit confirmation, while a revision the editor has not adopted is never the expected one. The transactional check runs on every attempt, so a further update blocks it again. Ownership and existing revision rules are unchanged. No version history, merging or collaboration.
- **Pending-deletion safety** (owner-approved). A delete is never reported as successful until the server acknowledges it. Offline deletes may simply fail with clear feedback. Pending, failed and unknown outcomes are represented as such, and signing out with an unresolved delete must not imply it succeeded. Online-first stays: no durable offline deletion queue.
- **Milestone 2: public GitHub source publication.** The approved destination is `Omar-Lyzkru/Online-Notes-App`, with public visibility and `main` as the intended default branch. Publication requires approval of the exact commit and external operations; the destination decision does not establish that publication has occurred. This milestone excludes application features, website deployment, and production Firebase actions. No license is being added; public visibility alone does not grant an open-source license.
- **Milestone 3: MVP completion and reliability** (owner-approved scope). Search of notes by title and content; appearance customization with preset background colors, light and dark themes and adjustable font sizes, in a simple settings interface; appearance preferences stored per user in Cloud Firestore and synchronized across the user's sessions; bounded corrections to the documented data-safety limitations (edits made while a delete is pending, the lifecycle of an uncertain delete notice, save/conflict feedback where needed to keep the existing invariants). Online-first stays: no offline editing, persistent cache, durable local drafts or durable offline queue; no custom backend, external search service, extra database or styling/state framework. The modified-client deletion limitation was to be investigated, not automatically fixed; the owner's decision on it is recorded below.
- **Deletion enforcement boundary** (owner-approved, Option 1). The supported application keeps its revision-aware transactional deletion (`deleteNote`), and Firestore rules keep enforcing per-user ownership. Firestore rules cannot compare a client-supplied revision on delete, so an authenticated modified client of the same owner can bypass the application's expected-revision protocol with a direct Firestore delete (emulator-verified); the owner accepted this limitation, and it stays disclosed in the documentation. The current design therefore does not provide server-enforced revision-aware deletion against such a client. No rules-enforced tombstone or backend-mediated deletion is part of M3. The acceptance covers only this limitation, not unrelated data-loss defects.
- **Appearance preference concurrency** (owner-approved). When two sessions change the same preference field at the same time, the later write wins. Changes to different preference fields made at the same time both survive. No further preference-conflict management is required: no revision counters, conflict dialogs or other synchronization protocol for preferences.
- Hosting deploy is planned, not done.

## Engineering choices (not owner decisions)
- Revision counter (`rev`) + transaction + rules for optimistic concurrency.
- Content stored as JSON string; 800 ms debounced autosave.
- Conflict choices offered to the user: keep mine, use other, save mine as copy.
- Deletion is a client-side Firestore transaction (read, compare `rev`, delete) in `deleteNote`. Security rules cannot compare a client-supplied revision on delete, so they keep enforcing ownership only. The expected revision is the one the editor shows when the user confirms (the open note's `baseRev`, including its own acknowledged saves, excluding remote changes it has not adopted).
- An unconfirmed delete is resolved only by server-authoritative listener data (a snapshot that is not from the cache, has no unacknowledged local writes, and no longer lists the note) or by a later definite answer to a new delete; a cached or optimistic disappearance is never treated as confirmation. Dismissing the notice does not forget the uncertainty (a persistent banner and sidebar marker remain for the session); it is in memory only.
- Milestone 3 implementation choices: search is client-side over the already loaded notes (every query word must occur in the title or the readable text; unsaved edits are not searched); appearance presets are five backgrounds (plain, paper, mint, sky, rose, each with a light and a dark variant), two themes and four text sizes, kept in sync between `src/appearance.ts` and `firestore.rules`; preferences are one document `users/{uid}/preferences/appearance`, written by a transaction that reads the stored document and applies only the touched fields, so a save never discards another session's change to a different field (this implements the approved concurrency policy above; offline saves fail visibly like note saves); a held draft is protected by deferring note switching while its delete is pending (sign-out may discard after an explicit warning); switching asks about an unresolved delete only when it concerns the open note, sign-out about all of them; reconciliation of an unconfirmed delete does not close an editor that holds unsaved edits; preferences are not cached in `localStorage` so other accounts on the same browser never inherit them.
