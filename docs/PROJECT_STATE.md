## Implemented
Auth UI (Google), notes CRUD, Tiptap editor with the five formats, autosave, conflict detection/recovery, Firestore rules, emulator config.

- **Leaving a note** (sign-out, switching): pending edits are saved first; otherwise the user must explicitly choose to discard. An unresolved delete is handled the same way (see below).
- **Deleting a note** is revision-aware: one Firestore transaction compares the revision the user was looking at with the stored one and deletes only on a match. A stale delete deletes nothing, says so, shows the newer note (or the usual conflict choices if there are unsaved edits), and needs a fresh confirmation. The note stays open until the server answers; notices distinguish pending, deleted (only after the server's answer), not deleted (offline, refused, changed elsewhere) and unconfirmed. Signing out or switching during an unresolved delete asks first.
- Emulator mode needs no `VITE_FIREBASE_AUTH_DOMAIN` (defaults to `localhost`). Verified against the local Firebase Auth emulator only, with synthetic identities: the popup opens at the emulator's handler (our scripted runs), and the emulator's simulated Google sign-in including its account chooser was exercised in a browser by the independent reviewer (not re-run by the implementation agent).
- A delete's answer can arrive after the user switched notes or while another note is open; it always ends in a terminal notice (deleted, not deleted, changed elsewhere, or unconfirmed), never a stuck "pending", and never touches another note. An unconfirmed notice resolves to "deleted (confirmed by the server)" once a server-authoritative snapshot (not from the cache, no unacknowledged local writes) no longer lists the note, whichever of the listener event and the notice arrives first; cached or optimistic disappearances do not resolve it.
- Tests: `npm test` — 84 tests (20 save-controller, 1 serialization, 3 Firebase config, 8 delete-outcome classification with a scripted transaction, 52 App/Editor UI tests in jsdom with Firebase and a lifecycle-aware Tiptap double). `npm run test:emulator` — 18 tests against the Firestore/Auth emulators (5 rules, 13 notes API: revision-aware deletion — match, stale refusal with content intact, repeated concurrent updates, cross-user denial, a delete/save race loop, a deterministic read-then-write interleaving, unreachable server — and listener-snapshot characterization of local versus server-delivered removals). Requires Java 21+.

## Not implemented
Search, appearance customization, MVP polish; deployment; offline editing; any durable offline deletion queue (offline deletes fail visibly by design). These features are outside the publication-only Milestone 2.

## Unverified
Real Google OAuth with a live or production Firebase configuration, and real Google account authorization — the local Auth emulator's simulated Google sign-in does not show that production OAuth (authorized domains, consent, real accounts) works; accessibility and small-screen layout beyond CSS review. The behaviors above were also exercised in headless Chrome on Windows against the emulators with scripted DOM events and simulated outages (not by hand with real input, not other browsers); the scripted scenarios are most reliable with a fresh Chrome process each: in one long-lived headless Chrome process, a later scenario (discarding a draft of a remotely deleted note) twice found the page's Firestore SDK stuck offline, identically on the pre-deletion code and not with a fresh process — attributed to the harness, not established. Atomicity is evidenced by the emulator transaction tests; the race loop is a stress test, not a proof.

## Known limitations
- Sidebar shows the last server title, not the in-progress draft title.
- Leaving a note waits up to 3 s for pending saves or an unresolved delete; if they cannot be settled the user may explicitly discard/leave. Drafts are not persisted locally (needs owner approval), so a session that ends without the prompt (expired token, sign-out in another tab) loses an unsaved draft and any unresolved delete's notice.
- The delete's revision check lives in the client transaction; Firestore rules cannot compare a revision on delete and still allow the owner to delete any revision (a modified client of the same owner could bypass the check).
- The SDK retries transactions on connection errors, so an offline delete can take about 10 s to report "not deleted", and a delete whose answer was lost may later be reported as "already deleted" or, if the connection stays down, as unconfirmed. An unconfirmed notice can be dismissed, which forgets the uncertainty.
- If the user edits a note while its delete is pending, those edits are kept only if the delete does not happen; if they switch away from the note meanwhile (after accepting the prompt), the edits are not saved even if the delete is then refused.
- Snapshot metadata cannot identify an online bare `deleteDoc` as optimistic; the app never issues one (deletes are transactions), so every removal it sees is server-delivered or flagged `fromCache`.
- Production bundle is ~1.2 MB (not code-split).
