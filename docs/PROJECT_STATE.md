# Project state

**Stage:** Milestone 3 (MVP completion and reliability) is implemented, passed independent review, was integrated into `main` by fast-forward (implementation commit `8a1bc17`, on top of the Milestone 2 baseline `2c31a41`), and was then published to GitHub: the public repository [Omar-Lyzkru/Online-Notes-App](https://github.com/Omar-Lyzkru/Online-Notes-App) holds Milestones 1–3, with the M3 integration-status commit `81d5f4b11a02c0f0b1c7207b5a71d43474fc6d23`. The app is **not** deployed and not production-ready. Milestone 4 (production readiness and deployment) has not started. The app runs only against local emulators; no live Firebase project, OAuth configuration, hosting or production rules were touched, and no deployment has been performed.

## Implemented
- **Notes:** Google sign-in/out (emulator-verified only), notes CRUD, Tiptap editor (bold, italic, headings, bullet lists, checklists), debounced autosave with server-acknowledged "Saved", revision-checked writes, explicit conflict recovery, Firestore rules, emulator config.
- **Deleting** is revision-aware: one Firestore transaction compares the revision the user was looking at with the stored one and deletes only on a match. A stale delete deletes nothing, says so, shows the newer note (or the usual conflict choices if there are unsaved edits) and needs a fresh confirmation. Notices distinguish pending, deleted (only after the server's answer), not deleted (offline, refused, changed elsewhere) and unconfirmed.
- **Leaving a note** (sign-out, switching): pending edits are saved first; otherwise the user must explicitly choose to discard. If the open note's delete is still waiting and the note holds unsaved edits (frozen until the server answers), switching is deferred instead of offered as a discard, so a refused delete still finds the draft; sign-out asks and says the edits are lost.
- **Unconfirmed deletes** stay visible for the session: dismissing the notice leaves a persistent banner and a ⚠ marker in the sidebar; sign-out and leaving that note ask; only server-authoritative data (or a later definite answer) clears it. Reconciliation never closes an editor that still holds unsaved edits.
- **Search:** client-side, title and readable body text of the user's own notes (Tiptap text nodes only, case-insensitive, all words must match), live with note changes, distinct "No notes yet" / "No notes match" states, never disturbs the open note.
- **Appearance settings:** light/dark theme, five background presets, four note text sizes, in a keyboard-operable Settings panel. Stored per user at `users/{uid}/preferences/appearance`, synchronized live between sessions, restored after reload, defaults when missing; "Saved" only after server acknowledgment, visible Not-saved/Retry state, remote updates never overwrite an unsaved local choice. Rules allow only the owner and only the fixed values.
- Emulator mode needs no `VITE_FIREBASE_AUTH_DOMAIN` (defaults to `localhost`).

## Not implemented
Deployment; offline editing or a persistent cache; durable local drafts; any durable offline deletion queue (offline deletes fail visibly by design); AI, sharing, folders, attachments (out of scope).

## Unverified
Real Google OAuth with a live or production Firebase configuration — the Auth emulator's simulated Google sign-in does not show that production OAuth (authorized domains, consent, real accounts) works. Browsers other than Chromium; assistive-technology behavior (keyboard operation and ARIA structure were checked, a screen reader was not); real touch devices. The browser scenarios are scripted (synthetic input and injected network faults), not hand-driven. Atomicity of the delete is evidenced by emulator transaction tests; the race loop is a stress test, not a proof. Firestore rules for preferences are tested in the emulator only; they are in the repository but have not been deployed.

## Known limitations
- Sidebar shows the last server title, not the in-progress draft title; search likewise reads saved content, not unsaved edits.
- Leaving a note waits up to 3 s for pending saves or an unresolved delete. Drafts are not persisted locally (needs owner approval), so a session that ends without the prompt (expired token, sign-out in another tab, closing the tab after the browser's own warning) loses an unsaved draft; the unconfirmed-delete record is in memory only and does not survive a reload.
- **Modified-client deletion (limitation accepted by the owner, Option 1):** The supported application deletes through a revision-aware client transaction (`deleteNote`), and Firestore rules enforce per-user ownership (another user cannot delete). Rules cannot compare a revision on delete and allow the owner to delete any revision, so a modified Firestore client signed in as the same owner can bypass the application's revision check with a direct `deleteDoc` (emulator-verified); the same client could also read the current revision and write a protocol-correct overwrite. The revision protocol therefore protects the owner's own sessions of the supported app from each other, not against a modified client of the same owner. The owner explicitly accepted this limitation for the current design; it remains disclosed here and in the README. No stronger enforcement (a rules-checked tombstone step, backend-mediated deletion) has been approved or implemented.
- With edits held by a pending delete, switching notes stays blocked until the server answers (usually seconds; the SDK gives up on an unreachable server after about 10 s); sign-out remains available with an explicit warning.
- The SDK retries transactions on connection errors, so an offline delete or preference save can take about 10 s to report failure (the UI shows "pending"/"Saving…" meanwhile), and a delete whose answer was lost may later be reported as "already deleted" or, if the connection stays down, as unconfirmed.
- Preferences (owner-approved policy): simultaneous changes to the same field end with the later write, and the two sessions then converge on it; simultaneous changes to different fields both survive (the save reads the stored document in a transaction and applies only the touched fields). There is no preference conflict UI or revision counter.
- Snapshot metadata cannot identify an online bare `deleteDoc` as optimistic; the app never issues one (deletes are transactions), so every removal it sees is server-delivered or flagged `fromCache`.
- Production bundle is ~1.2 MB (not code-split).
