# Architecture (as implemented)

- **Frontend** (`src/`): React SPA. `App.tsx` handles auth state (loading/signed-out/signed-in, errors) and renders `Notes` keyed by uid, so sign-out unmounts it and tears down the listener and all note state. `Editor.tsx` hosts Tiptap and the status/conflict UI and hands the parent an `EditorHandle` (`state`, `settle`, `hold`, `release`, `review`, `abandon`). The save state lives only in the open note's `SaveController`; `App` never mirrors it, so nothing stale can outlive an editor.
- **Auth:** Firebase Auth `signInWithPopup(GoogleAuthProvider)`; `onAuthStateChanged` gates the UI. Emulators are used when `VITE_USE_EMULATORS=true`.
- **Data:** `users/{uid}/notes/{id}` = `{title, content (Tiptap JSON string), rev, createdAt, updatedAt}`.
- **Sync:** one `onSnapshot` on the user's notes collection (metadata changes included, so a cache-only state is shown as "not connected"). Deleting and creating propagate through it.
- **Saving** (`saveController.ts`, `notesApi.ts`): edits are debounced (800 ms) into one write. `saveNote` runs a Firestore transaction: reads the note, requires `rev === baseRev`, writes `rev + 1`. Transactions need the server, so offline saves fail visibly instead of queueing. State machine: saved → dirty → saving → saved | error | conflict.
- **Leaving a note** (sign-out or opening another note, `leaveNote` in `App.tsx`): pending edits are first driven to a resting state with `SaveController.settle()` (waits for a write in flight, flushes a dirty draft, retries a failed one once; conflicts are left alone), waiting at most 3 s. A delete that is still pending (or whose outcome is unknown) is handled first: leaving waits up to 3 s for its answer, then asks the user to accept that the outcome is unknown (Cancel stays). Only if everything is saved does the action proceed silently; otherwise the user gets one explicit choice, and Cancel keeps the signed-in session, the open note and the draft. Remote deletion handled by the editor itself (`Discard my draft` / `Restore my draft`) is already an explicit choice and asks nothing more.
- **Deleting a note** (`requestDelete` in `App.tsx`, `deleteNote` in `notesApi.ts`): after the user confirms, `EditorHandle.hold()` pauses autosave and freezes remote changes for that note, waits for the note's own write in flight, and returns the revision on screen (`baseRev`). `deleteNote(db, uid, id, expectedRev)` then runs one Firestore transaction: read the note; absent → `'already-deleted'`; `rev !== expectedRev` → `ConflictError(current note)` and nothing is deleted; otherwise `tx.delete`. The commit carries a precondition on the document that was read, so a write landing in between makes the SDK retry the callback, which then fails the check. The note stays open, with its draft, until the server answers:
  - `deleted` / `already-deleted`: `abandon()` closes the controller for good, the note closes, and the notice says so (the only success messages).
  - `ConflictError`: `release()` resumes the editor and `review(remote)` feeds it the newer note (adopted if the editor is clean; otherwise the usual conflict choices with the draft). The notice says nothing was deleted. Deleting again needs a new confirmation and uses the revision then on screen, so a further update blocks it again.
  - failure before anything reached the server (offline, permission): "not deleted", note and draft kept, editing resumes, Delete can be retried.
  - `DeleteOutcomeUnknownError` (the connection failed after a delete had been sent; the SDK retries transactions, so any attempt may have committed): "could not confirm", the note stays. It becomes "deleted (confirmed by the server)" only through the reconciliation described below.
  A pending delete disables the Delete button and shows a "has not been deleted yet" notice; duplicate clicks do nothing.
  **Late answers.** The server's answer can arrive after the user switched notes (the note's editor is unmounted and its Tiptap instance destroyed) or signed out. `requestDelete` therefore sets the terminal notice first and only then touches the editor, best-effort (`withEditor`, errors swallowed); the editor handle's `release`/`review` are no-ops once that editor unmounted (a flag in `Editor.tsx`; `SaveController.release()` also refuses after `dispose()`). The delete flow does not rely on the controller being usable after unmount, and `dispose()` is not a general write barrier: it only cancels the controller's pending autosave timer and makes `release()` a no-op. `flush()` and `edit()` do not check it; unmounting itself makes a best-effort `flush()` of unsaved edits first (skipped while a delete holds the note); and a save already in flight at unmount keeps going and, if the draft changed during it, its completion can still schedule one follow-up flush. The barrier that stops all further writes is `abandon()` (`closed`), applied only after the server confirmed a delete; `hold()` (`held`) blocks saving and remote changes while a delete is pending. A `finally` safety net turns any attempt that somehow ended without a terminal notice into "could not confirm", so the pending state and the disabled Delete button cannot outlive an answer. When the refused note is not open, the conflict notice says to open it again; reopening mounts a fresh editor from the latest snapshot, and deleting again needs a new confirmation on the revision then on screen. A late result concerns only the note it was issued for (`id` in the notice); it never touches another note's editor or state.
  **Reconciling an unconfirmed outcome.** An "unknown" notice is replaced by "deleted (confirmed by the server)" only when the latest listener snapshot (`subscribeNotes`) meets all of: it is not from the cache (`fromCache` false), none of its documents carries an unacknowledged local write (`hasPendingWrites` false) — in `App.tsx`, `authoritative = !fromCache && !pendingWrites` — and it no longer lists the note. A cached snapshot (for example while offline) or one that includes unacknowledged local writes never resolves the notice, and neither does a snapshot that still lists the note; the notice then stays "could not confirm" until server-originated data arrives. The check runs on every change of snapshot, authority flag or notice, so it does not matter whether the listener event or the notice comes first. It applies only to the "unknown" notice; a "pending" delete is resolved by its own transaction's answer. Limits (verified against the emulator): `hasPendingWrites` describes the documents in the snapshot, so it cannot flag a locally deleted note, and these flags cannot tell an online bare `deleteDoc` from a server event. The app therefore relies on never issuing one — deletes are transactions, which cause no optimistic local event — rather than on the flags detecting it. An offline local removal is flagged `fromCache` and is not accepted until reconnected.
- **Remote updates:** applied only when the editor is clean. The editor re-evaluates the latest snapshot whenever the save state changes (not only when the snapshot does), so a revision that arrived during a write is handled once it is acknowledged. If a draft exists (dirty/error), the controller enters `conflict`, keeps the draft, and the user picks: keep mine (rebase on remote rev, overwrite), use other (discard mine), or save mine as a new note. A remote deletion with a draft offers restore or discard.
- **Security:** `firestore.rules` — owner-only via path uid, field whitelist, create requires `rev == 1`, update requires `rev == old + 1` and unchanged `createdAt`; delete is owner-only. Rules cannot see a client revision on delete, so the revision check on delete is the client transaction above (it protects the owner's own sessions from each other, not against a modified client of the same owner).
- **Caching:** default in-memory Firestore cache; no persistence.
