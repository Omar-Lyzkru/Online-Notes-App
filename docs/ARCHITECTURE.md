# Architecture (as implemented)

- **Frontend** (`src/`): React SPA. `App.tsx` handles auth state (loading/signed-out/signed-in, errors) and renders `Notes` keyed by uid, so sign-out unmounts it and tears down the listener and all note state. `Editor.tsx` hosts Tiptap and the status/conflict UI and hands the parent an `EditorHandle` (`state`, `settle`, `hold`, `release`, `review`, `abandon`). The save state lives only in the open note's `SaveController`; `App` never mirrors it, so nothing stale can outlive an editor. `Settings.tsx` is the appearance panel; `search.ts` and `appearance.ts` are small pure modules (see Search and Appearance below).
- **Auth and access** (`App.tsx`, `AccessDenied.tsx`): Firebase Auth `signInWithPopup(GoogleAuthProvider)` with `prompt=select_account` (so a refused account can be switched); `onAuthStateChanged` gates the UI. Authenticating is not authorization: any Google account can authenticate, but only an allowlisted uid is served data (see Security). `Notes` (keyed by uid) subscribes to the user's notes; a `permission-denied` on that listen **before any server snapshot arrived** (a cache-only snapshot does not count) means the account is not allowlisted, and `Notes` renders `AccessDenied` (who is signed in, "not authorized", a direct Sign out; there is no draft to protect) instead of the notebook. The screen reads no allowlist data and shows no uid or Firestore error text. A `permission-denied` after a server snapshot (access revoked mid-session) is only an error banner: the notebook and any draft stay on screen. Emulators are used only by the dev server (see Configuration).
- **Data:** `users/{uid}/notes/{id}` = `{title, content (Tiptap JSON string), rev, createdAt, updatedAt}`. `users/{uid}/preferences/appearance` = `{theme, background, fontSize, updatedAt}` (see Appearance).
- **Sync:** one `onSnapshot` on the user's notes collection (metadata changes included, so a cache-only state is shown as "not connected"). Deleting and creating propagate through it.
- **Saving** (`saveController.ts`, `notesApi.ts`): edits are debounced (800 ms) into one write. `saveNote` runs a Firestore transaction: reads the note, requires `rev === baseRev`, writes `rev + 1`. Transactions need the server, so offline saves fail visibly instead of queueing. State machine: saved → dirty → saving → saved | error | conflict.
- **Leaving a note** (sign-out or opening another note, `leaveNote` in `App.tsx`). In order: (1) a delete still in flight gets up to 3 s to answer; (2) if the open note is the one being deleted, the delete is still waiting and the note holds unsaved edits (they are frozen by `hold()` and cannot be saved until the server answers), **switching is deferred**: nothing happens except a notice that the edits are kept, and the user can try again once the delete has answered (refused: the draft and the usual conflict choices are still there). Sign-out in that state asks, saying plainly that the edits are lost even if the delete is then refused; (3) otherwise pending edits are driven to a resting state with `SaveController.settle()` (waits for a write in flight, flushes a dirty draft, retries a failed one once; conflicts are left alone), waiting at most 3 s; (4) if something is still unsaved, or a delete is unresolved (waiting, or answered with "unknown"), one explicit question lists everything at stake and Cancel keeps the signed-in session, the open note and the draft. Switching only cares about an unresolved delete *of the open note*; signing out about any of them. If everything is saved and nothing is unresolved the action proceeds silently. Remote deletion handled by the editor itself (`Discard my draft` / `Restore my draft`) is already an explicit choice and asks nothing more.
- **Deleting a note** (`requestDelete` in `App.tsx`, `deleteNote` in `notesApi.ts`): after the user confirms, `EditorHandle.hold()` pauses autosave and freezes remote changes for that note, waits for the note's own write in flight, and returns the revision on screen (`baseRev`). `deleteNote(db, uid, id, expectedRev)` then runs one Firestore transaction: read the note; absent → `'already-deleted'`; `rev !== expectedRev` → `ConflictError(current note)` and nothing is deleted; otherwise `tx.delete`. The commit carries a precondition on the document that was read, so a write landing in between makes the SDK retry the callback, which then fails the check. The note stays open, with its draft, until the server answers:
  - `deleted` / `already-deleted`: `abandon()` closes the controller for good, the note closes, and the notice says so (the only success messages).
  - `ConflictError`: `release()` resumes the editor and `review(remote)` feeds it the newer note (adopted if the editor is clean; otherwise the usual conflict choices with the draft). The notice says nothing was deleted. Deleting again needs a new confirmation and uses the revision then on screen, so a further update blocks it again.
  - failure before anything reached the server (offline, permission): "not deleted", note and draft kept, editing resumes, Delete can be retried.
  - `DeleteOutcomeUnknownError` (the connection failed after a delete had been sent; the SDK retries transactions, so any attempt may have committed): "could not confirm", the note stays. It becomes "deleted (confirmed by the server)" only through the reconciliation described below.
  A pending delete disables the Delete button and shows a "has not been deleted yet" notice; duplicate clicks do nothing.
  **Late answers.** The server's answer can arrive after the user switched notes without edits (switching with held edits is deferred, see above), or signed out; the note's editor is then unmounted and its Tiptap instance destroyed. `requestDelete` therefore sets the terminal notice first and only then touches the editor, best-effort (`withEditor`, errors swallowed); the editor handle's `release`/`review` are no-ops once that editor unmounted (a flag in `Editor.tsx`; `SaveController.release()` also refuses after `dispose()`). The delete flow does not rely on the controller being usable after unmount, and `dispose()` is not a general write barrier: it only cancels the controller's pending autosave timer and makes `release()` a no-op. `flush()` and `edit()` do not check it; unmounting itself makes a best-effort `flush()` of unsaved edits first (skipped while a delete holds the note); and a save already in flight at unmount keeps going and, if the draft changed during it, its completion can still schedule one follow-up flush. The barrier that stops all further writes is `abandon()` (`closed`), applied only after the server confirmed a delete; `hold()` (`held`) blocks saving and remote changes while a delete is pending. A `finally` safety net turns any attempt that somehow ended without a terminal notice into "could not confirm", so the pending state and the disabled Delete button cannot outlive an answer. When the refused note is not open, the conflict notice says to open it again; reopening mounts a fresh editor from the latest snapshot, and deleting again needs a new confirmation on the revision then on screen. A late result concerns only the note it was issued for (`id` in the notice); it never touches another note's editor or state.
  **Unconfirmed outcomes.** A delete that ends as "unknown" is recorded in `unconfirmed` (note id → title, in `Notes`), separate from the dismissible notice. Dismissing the notice therefore does not forget it: while the session is active a persistent banner ("Still unconfirmed … it may still exist") and a ⚠ marker on the note in the sidebar remain, sign-out asks about every unconfirmed note, and leaving the note itself asks. It is cleared only by (a) server-authoritative data showing the note gone (below), (b) a later delete of that note getting a definite answer (`deleted` / `already-deleted`, or a refusal that returned the note, which proves it exists), never by a plain failure such as "offline". Several unconfirmed notes can coexist; a new notice never replaces another's entry. The state is in memory only: it does not survive a reload, which is the approved online-first limit.
  **Reconciling an unconfirmed outcome.** An entry is replaced by "deleted (confirmed by the server)" only when the latest listener snapshot (`subscribeNotes`) meets all of: it is not from the cache (`fromCache` false), none of its documents carries an unacknowledged local write (`hasPendingWrites` false) — in `App.tsx`, `authoritative = !fromCache && !pendingWrites` — and it no longer lists the note. A cached snapshot (for example while offline) or one that includes unacknowledged local writes never resolves it, and neither does a snapshot that still lists the note; it then stays unconfirmed until server-originated data arrives or the user deletes again. The check runs on every change of snapshot, authority flag, notice or unconfirmed set, so the order of the listener event and the answer does not matter, and it waits while another delete is pending so it never replaces that notice. If the open editor still holds unsaved edits when the note disappears, the note is **not** closed: the editor offers the usual remote-deletion choices (Restore / Discard my draft). Limits (verified against the emulator): `hasPendingWrites` describes the documents in the snapshot, so it cannot flag a locally deleted note, and these flags cannot tell an online bare `deleteDoc` from a server event. The app therefore relies on never issuing one — deletes are transactions, which cause no optimistic local event — rather than on the flags detecting it. An offline local removal is flagged `fromCache` and is not accepted until reconnected.
- **Search** (`search.ts`, used by `Notes` in `App.tsx`): entirely client-side over the user's own notes, which the notes listener already delivers; no extra query, index service or write. `noteText(content)` walks the Tiptap JSON and collects only the `text` of text nodes (block nodes end a line; adjacent runs of one word, e.g. bold in the middle, stay joined), so node names, mark names, attributes and JSON keys are never matched; invalid content yields no text. `indexNotes` keeps a lowercase title + body string per note, rebuilt only when that note's title or content changed; `searchNotes` requires every whitespace-separated word of the query to occur in it (case-insensitive, regex characters literal). An empty query is the normal list. The index follows every snapshot, so created, edited, renamed, deleted and remotely synchronized notes are reflected; it reads the *saved* server version, so an open note's unsaved edits are not searched. Searching never writes and never touches the open editor: a note that does not match stays open and its draft untouched. "No notes yet" (empty notebook) and "No notes match …" (with a Clear search button) are distinct; creating a note clears the query so the new note is visible.
- **Appearance** (`appearance.ts`, `preferencesApi.ts`, `preferencesController.ts`, `usePreferences.ts`, `Settings.tsx`, `styles.css`): three choices — theme (light/dark), background preset (plain, paper, mint, sky, rose; each has a light and a dark variant) and note text size (small 14 px … extra large 23 px) — stored in one document `users/{uid}/preferences/appearance`. The page root carries `data-theme`, `data-bg`, `data-font`; `styles.css` turns them into CSS variables (everything else — surfaces, banners, status colors — is derived from them, and `color-scheme` follows the theme). `Notes` (keyed by uid) mounts `usePreferences(uid)`: one `onSnapshot` on the document, and on unmount the listener stops and the attributes are removed, so a different user or the signed-out screen never inherits them (nothing is kept in `localStorage`). A missing document, or a missing/unknown field, uses the default for that field. **Saving** is a transaction (`savePreferences`) that writes only the changed fields on top of what the server holds, so, like note saves, it needs the server (offline it fails visibly rather than queueing) and resolves only after the acknowledgment. `PreferencesController` shows a choice immediately but reports "Saving…" until acknowledged, "Not saved" with Retry (and automatic retry on reconnect) after a failure, and "Saved to your account" only after the ack; a remote update never replaces a field that has an unsaved local choice and applies to all other fields. Concurrent changes to different fields from two sessions both survive; for the same field the later write wins (it is a setting, there is no per-field conflict UI). The panel is a labelled non-modal dialog of native radio groups, so it is keyboard-operable (Escape closes and returns focus to the Settings button).
- **Remote updates:** applied only when the editor is clean. The editor re-evaluates the latest snapshot whenever the save state changes (not only when the snapshot does), so a revision that arrived during a write is handled once it is acknowledged. If a draft exists (dirty/error), the controller enters `conflict`, keeps the draft, and the user picks: keep mine (rebase on remote rev, overwrite), use other (discard mine), or save mine as a new note. A remote deletion with a draft offers restore or discard.
- **Security:** `firestore.rules` — **allowlist and ownership**: `isOwner(uid)` is `request.auth.uid == uid` **and** `isAllowlisted()`, which requires a document `authorizedUsers/{request.auth.uid}` that exists and whose `active` field is boolean `true` (`exists()`/`get()`; a missing document, `false`, another type or a missing field all deny, so the rules fail closed, and an empty allowlist denies everyone). Both conditions apply to every read, list, create, update and delete of notes and preferences. The check keys on the caller's own uid, never on a client-supplied field or an email. `match /authorizedUsers/{member}` is `allow read, write: if false`, so no client (approved or not, signed in or not, singly or in a batch) can read, list, add, change or remove membership, and no other path can influence the check; a final `match /{path=**}` denies everything not listed. Membership is created and removed only with privileged access (Firebase console, or Admin credentials; both bypass rules): there is no bootstrap path in the app and no backend. No uid or email appears in the rules or anywhere in the repository. Each evaluated request is billed one extra document read for the membership document. The rest of the rules are unchanged: owner-only via path uid, field whitelist, create requires `rev == 1`, update requires `rev == old + 1` and unchanged `createdAt`; delete is owner-only. Preferences: `users/{uid}/preferences/appearance` is readable and writable only by that uid, with exactly the keys `theme`, `background`, `fontSize`, `updatedAt`, each of `theme`/`background`/`fontSize` one of the fixed values (the same lists as `appearance.ts`; a rules test checks every value the app offers is accepted and others are rejected), `updatedAt` equal to the server time, and no delete; every other path under a user is denied by default. **What the revision check does and does not protect (investigated, see `tests/emulator/deleteBoundary.test.ts`):** rules cannot see a client-supplied revision on delete, so the revision check on delete is the client transaction above. It protects the owner's own sessions of the supported application from each other. A modified client of the same owner can `deleteDoc` any revision (verified), and could equally read the current revision and write a protocol-correct overwrite (verified), because for the owner's own data the rules can only check consistency, not intent. Cross-user access is denied for all of it. A stricter, rules-only variant (delete only after an acknowledged update that tombstones the note) would also refuse a bare `deleteDoc` from clients that do not follow the protocol, but would not stop a modified client either, and it changes the data model and the rules; it is not implemented (an owner decision, see `DECISIONS.md`).
- **Configuration and environments** (`firebaseConfig.ts`, `firebase.ts`, `emulators.ts`, `main.tsx`, `vite.config.ts`): `resolveFirebaseSetup(env, production)` returns `emulator` or `live` options, or throws a `ConfigError` listing every problem; it never falls back to placeholders. Dev server (`!import.meta.env.PROD`): emulators unless `VITE_USE_EMULATORS=false`, which then requires the full live web config. Production build: always live; requires `VITE_FIREBASE_API_KEY/AUTH_DOMAIN/PROJECT_ID/APP_ID`, an auth domain that is `<project>.firebaseapp.com` or `<project>.web.app` for that project, a non-`demo-` project id, a web app id, and refuses `VITE_USE_EMULATORS=true`. This is enforced at build time (`vite.config.ts`, which also refuses `NODE_ENV` other than `production`, because `import.meta.env.PROD` follows `NODE_ENV`) and checked again at startup in `main.tsx`, which shows the problems on the page and does not load the app. `firebase.ts` references `emulators.ts` only behind the compile-time `!PROD`, so production bundles contain no emulator options or endpoints (asserted by a test that runs a real build, and by `scripts/verify-dist.mjs`). Web config values identify the project and are not secrets; service-account keys and admin tokens are never used by the app and never belong in `VITE_*` variables (browser-shipped) or the repository. Local env files and `.firebaserc` are Git-ignored; there is no default Firebase project, so every CLI command must say `--project`.
- **Hosting and release** (`firebase.json`, `docs/DEPLOYMENT.md`): Firebase Hosting serves the Vite output `dist/` over HTTPS at the project's default site. Hashed assets are immutable-cached, `/` and `/index.html` are `no-cache` (a stale index would point at deleted assets), security headers are set, nothing outside `dist/` is served, and there are no rewrites (no client-side routes). Releases are rules first (`firebase deploy --only firestore:rules`), then Hosting (`--only hosting`), each separately authorized and each naming the project. Hosting rollback restores only the static site; Firestore data and the allowlist are independent of it and are never changed by a rollback. `ops/lockdown/` is a deny-all ruleset for recovery.
- **Data boundaries:** the browser holds only the signed-in user's own documents; no secret is in the bundle; the allowlist is unreachable from clients; the supported app's revision-aware deletion is a client transaction, while server-side rules enforce authorization and ownership only (a modified client of the approved owner can still bypass the expected-revision delete: accepted by the owner, unchanged).
- **Caching:** default in-memory Firestore cache; no persistence.
